## Phase Details

### Phase 12: Правка и удаление записей истории

**Goal**: Оператор исправляет собственные ошибки ввода в истории устройства — правит любую запись (сотрудник, дата, тип действия, комментарий) или удаляет её целиком — и учёт остаётся непротиворечивым: таймлайн и текущее состояние устройства (держатель, статус) отражают правку сразу, потому что выводятся из исправленной истории.
**Depends on**: Nothing (первая фаза вехи; строится на отгруженном v1.1)
**Requirements**: HIST-01, HIST-02, HIST-03
**Success Criteria** (what must be TRUE):

  1. На карточке устройства оператор открывает существующую запись истории и исправляет сотрудника, дату, тип действия и комментарий; исправленная запись встаёт на своё место в таймлайне (порядок по дате)
  2. Оператор удаляет ошибочную запись из таймлайна после явного подтверждения — запись исчезает из истории
  3. После правки или удаления текущий статус устройства (держатель, статус) обновляется сразу во всех местах показа: карточка устройства, строка реестра, список «выданного» у сотрудника — выводится из исправленной истории, а не остаётся от старой (например, удаление последней «выдачи» возвращает устройство на склад)
  4. Правка применяет те же правила валидации, что и создание записи: дата с учётом DISPLAY_TZ (Europe/Moscow), тип действия из фиксированного набора, существующий сотрудник справочника; невалидные изменения не сохраняются с внятной ошибкой
  5. Инвариант append-only для `movements` снимается миграцией в цепочке миграций проекта (воспроизводимо на сервере через установленный путь миграции — не ручной правкой базы и не обходом триггеров в коде); все существующие потоки работают как раньше — добавление записей, bulk-выдача/приём, клонирование, «Списать»

**Plans**: 1/2 plans executed
Plans:
**Wave 1**

- [x] 12-01-PLAN.md — Миграция 0002 снимает append-only; keystone edit-схемы + occurredAtDateIso; replay-движок editMovement/deleteMovement с проекцией (HIST-01..03 data, SC5)

**Wave 2** *(blocked on Wave 1 completion)*

- [x] 12-02-PLAN.md — Timeline client-остров с триггерами на строках, диалоги «Исправить запись»/«Удалить запись?», Server Actions, UAT (HIST-01..03 UI)

**UI hint**: yes

### Phase 13: Удаление устройств

**Goal**: Оператор удаляет ошибочно добавленное устройство целиком одним подтверждённым действием — вместе с его историей — и устройство гарантированно исчезает со всех поверхностей учёта: реестр, поиск, ⌘K-палитра, дашборд, CSV-выгрузка.
**Depends on**: Phase 12 (каскадное удаление истории требует снятого DELETE-триггера на `movements`)
**Requirements**: DEL-01, DEL-02
**Success Criteria** (what must be TRUE):

  1. На карточке устройства оператор удаляет устройство одним действием с явным подтверждением; после подтверждения карточка исчезает, а её старый URL отвечает 404 (контракт 404-матрицы фазы 2)
  2. История уходит вместе с устройством: записи movements удаляются каскадом в одной транзакции — осиротевших записей не остаётся, лента дашборда больше не показывает устройство
  3. Устройство исчезает со всех поверхностей: реестр (список и фильтры), substring-поиск по серийнику/инвентарнику/модели, ⌘K-палитра, счётчики и лента дашборда, обе CSV-выгрузки — parity через общий deviceWhere
  4. Удаление ≠ списание: действие «Списать» работает как раньше; удаление устройства не создаёт записи «списание» и не архивирует устройство
  5. Карточки сотрудников остаются корректными: удалённое устройство исчезает из списка «выданного» у сотрудника; другие устройства и счётчики не задеты
