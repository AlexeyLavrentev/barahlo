# Roadmap: Barahlo — учёт корпоративной техники

## Overview

Путь от пустого каркаса до замены электронной таблицы: сначала фундамент, на котором данным можно доверять с первого дня (полная схема БД с append-only историей перемещений, единый вход, авторизация на всём, автоматические бэкапы), затем люди и техника (справочник сотрудников, реестр устройств с полями на тип), затем транзакционное ядро владения (выдача/возврат/передача одним действием + неизменяемый таймлайн + фото), и только потом — то, ради чего всё это: мгновенный поиск, фильтры («ноуты без апгрейда RAM»), подсветка гарантии и дашборд. Порядок продиктован зависимостями и исследованием: всё, что нельзя починить потом (схема, нормализованные номера, миграции), делается до появления данных.

**Granularity:** standard (6 фаз). Фаза «Фото» слита с «Владением» (одиночное требование REG-05; фото зависят только от реестра устройств).

## Phase Details

### Phase 1: Foundation

**Goal**: Развёрнутый на внутреннем сервере каркас приложения, на котором данным можно доверять с первого дня: полная схема SQLite v1 (включая append-only `movements` и нормализованные номера), единый вход, авторизация на каждом маршруте, автоматические бэкапы с отрепетированным восстановлением.
**Mode:** mvp
**Depends on**: Nothing (first phase)
**Requirements**: ACC-01, ACC-02, ACC-03
**Success Criteria** (what must be TRUE):

  1. Открытие любого адреса приложения без сессии всегда приводит к странице входа; страницы, API и файлы (включая будущие фото) недоступны без авторизации
  2. Вход по логину+паролю работает: неверные данные не пускают (перебор ограничен), верные — пускают; сессия сохраняется между открытиями браузера
  3. Все данные живут в одном SQLite-файле: миграция с первого дня создаёт полную схему v1 — устройства, сотрудники, append-only перемещения (события нельзя перезаписать), вложения, нормализованные серийные/инвентарные номера с индексами (задел под MOVE-04, FIND-01, FIND-04)
  4. Бэкап БД и загрузок создаётся автоматически по расписанию, и восстановление из бэкапа успешно отрепетировано хотя бы один раз
  5. Приложение работает на внутреннем сервере одним контейнером; данные — в примонтированном томе и переживают перезапуск

### Phase 3: Device Registry

**Goal**: Техника вносится в реестр: четыре фиксированных типа с наборами полей на тип (keystone-модуль `device_schema.ts` — единый источник форм, валидации и будущих фильтров), редактирование, быстрые серверные списки. Сердце приложения и фундамент фаз 4–6.
**Mode:** mvp
**Depends on**: Phase 1, Phase 2 (сотрудники как справочник; устройства ссылаются на сотрудников только с Фазы 4)
**Requirements**: REG-01, REG-02, REG-03
**Success Criteria** (what must be TRUE):

  1. Пользователь создаёт устройство любого из 4 типов (ноутбук / монитор / док-станция / периферия) — форма показывает поля именно этого типа; на карточке видны общие поля: модель, серийник, инвентарник, RAM, флаг «RAM апгрейдена», SSD, закупка (дата, поставщик), стоимость, гарантия до, заметки
  2. Пользователь редактирует все поля устройства; набор полей и валидация жёстко определяются типом и enforced приложением
  3. Реестр листается по типам с серверной пагинацией — список быстрый уже на старте
  4. Статус и владелец не редактируются в форме устройства напрямую — состояние меняется только действиями выдачи/возврата/ремонта/списания (строятся в Фазе 4); защита от «протухшего» статуса заложена с первого экрана

### Phase 4: Custody & Photos

**Goal**: Транзакционное ядро — причина существования приложения: выдача/возврат/передача одним действием, атомарно пишущие событие в неизменяемую историю и обновляющие текущее состояние; карточки устройств и сотрудников всегда показывают актуального держателя; к устройству прикладываются фото.
**Mode:** mvp
**Depends on**: Phase 3 (устройства), Phase 2 (сотрудники)
**Requirements**: MOVE-01, MOVE-02, MOVE-03, MOVE-04, MOVE-05, REG-04, EMP-02, REG-05
**Success Criteria** (what must be TRUE):

  1. «Выдать» устройство сотруднику — одно действие: держатель, статус и запись в истории меняются атомарно, одной транзакцией
  2. «Принять» на склад и «Передать» другому сотруднику — такие же одноразовые действия; карточка устройства и карточка сотрудника (список выданной техники) обновляются мгновенно
  3. Таймлайн на карточке устройства показывает всю историю: кто, когда, от кого/кому, начиная с «поступления»; события нельзя отредактировать или удалить — ошибка исправляется новым компенсирующим событием
  4. Статусы «в ремонт» / «из ремонта» / «списано» ставятся только действиями (не правкой полей); списанное устройство остаётся в базе с полной историей
  5. Пользователь прикладывает фото к карточке устройства (в том числе с телефона); миниатюры видны в списках; фото отдаются только авторизованным

**Goal**: Главный продукт и момент Core Value: мгновенный точный ответ — нашёл устройство по фрагменту номера, отфильтровал «ноуты без апгрейда RAM» одним кликом, увидел истекающую гарантию; всё это летает на сотнях устройств.
**Mode:** mvp

  5. На сотнях устройств поиск, фильтры и пагинация остаются мгновенными (серверные списки, индексированные колонки)

Маппинг-решения (осознанные, не потери):

- **REG-04 (установить статус) → Фаза 4**, а не Фаза 3: статус меняется только действиями выдачи/возврата/ремонта/списания (главный pitfall исследования — «status drift»); в Фазе 3 формы статуса не содержат.
- **EMP-02 (карточка с выданной техникой) → Фаза 4**: список выданного становится проверяемым только когда технику можно выдать; экран карточки строится в Фазе 2.
- **REG-05 (фото) → Фаза 4**: одиночное требование слито с ядром владения по калибровке гранулярности; зависимости не нарушены (фото требуют только устройств).
- **UI-01, UI-02 → Фаза 2** (первые полноценные экраны задают язык и эстетику), **UI-03 → Фаза 5** (скорость поиска/фильтров на сотнях устройств проверяется там, где появляется поиск).
