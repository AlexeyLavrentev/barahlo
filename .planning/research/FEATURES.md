# Feature Research: Manager-Convenience Features (v1.3 «Удобство и выгрузка»)

**Domain:** внутренний инструмент учёта техники для одного руководителя (50–200 сотрудников, сотни устройств)
**Researched:** 2026-09-29
**Confidence:** MEDIUM (landscape HIGH for Snipe-IT official features; MEDIUM for RU act practice; LOW–MEDIUM for SaaS blog-level claims on alerts/reports)
**Context already scoped for v1.3 (not researched here):** XLSX-выгрузка, лайтбокс фото.

**Complexity scale (honest, single-dev):** S = дни, один сегмент фазы; M = полноценная фаза с UAT; L = несколько фаз или высокий риск регрессии. Все кандидаты ниже — S/M; ничего L не рекомендовано.

## What Single Managers Actually Use Daily

Cross-referencing Snipe-IT (official feature set), Asset Panda (mobile-first SaaS) and generic ITAM practice, the daily loop of a one-person asset manager has four recurring moments:

1. **Lookup** («где серийник X», «у кого ноут без RAM-апгрейда») — Barahlo уже силен: поиск, ⌘K, фильтры, дашборд. Research не предлагает здесь ничего нового.
2. **Issue/return loop** (самое частое действие: выдать/принять) — Snipe-IT строит вокруг этого «one-click checkin» и поиск→выдача; здесь у Barahlo есть трение (открыть карточку → диалог).
3. **Periodic review** (раз в неделю/месяц: гарантия, закупки, отчёт начальству) — частично покрыто дашбордом; XLSX (v1.3) закрывает «отдать файл».
4. **Поступление новой партии** (закупил 50 ноутов → клон ×50 → раздать) — клон есть; раздача = bulk; бумага и наклейки — нет.

Каждый кандидат ниже привязан к одному из этих моментов. Признак «используется ежедневно» — главный фильтр против scope creep.

## Feature Landscape

### Table Stakes (для этого продукта — без них ежедневный цикл ощущается недоделанным)

| Feature | Why Expected | Complexity | Notes |
|---------|--------------|------------|-------|
| **Сохранённые фильтры/виды** (закрепить текущий URL-фильтр под именем: «Ноуты без RAM», «Гарантия < 60 дн», «Отдел поддержки») | Болезнь-прародитель приложения — повторяющиеся вопросы; в SaaS saved searches — стандарт (Asset Panda), а повторный набор фильтров = трение каждый раз. Дашборд уже даёт 1–2 жёстких deep-link'а — saved views обобщают это до пользовательских | **S** | Ключевой инсайт: фильтры и поиск УЖЕ синхронизированы в URL. Сохранённый вид = имя + строка URL. Для одного пользователя достаточно localStorage — без миграции БД, без сервера. Чипы-закладки над списком + управление (переименовать/удалить/по умолчанию). Дешёво и обратимо |
| **Быстрые действия из списка** («Принять»/«Выдать» прямо на строке устройства, без открытия карточки) | Самое частое действие дня; у Snipe-IT это буквально «one-click checkin», и гайды по Snipe-IT описывают рабочий цикл «нашёл поиском → выдал». Сейчас: карточка → действие → диалог. Один клик экономии × десятки раз в неделю | **S–M** | Реюз существующих bulk-диалогов в одиночном режиме (bulk-панель уже умеет «один диалог на партию» — переиспользовать тот же server action). Риск: чекбокс + кнопки в одной строке = визуальный шум и миссклики (прецедент «чекбокс — сиблинг Link'а»); нужна аккуратная раскладка строки. Одно действие на строку, не меню из 5 |
| **Мобильная эргономика (полировка, не фича)** | Фото снимаются с телефона (уже работает), QR-этикетки (ниже) открывают карточку с телефона — ключевые поверхности (карточка устройства, списки, формы приёма) должны быть удобны пальцем на маленьком экране внутренней сети | **S** | Responsive-аудит + тач-таргеты + крупный шрифт диалогов на телефоне. Без новых функций. Логично идти сразу за лайтбоксом (v1.3) — одна волна UI-правок |

### Differentiators (конкурентное преимущество; главный пул для выбора скоупа v1.3)

| Feature | Value Proposition | Complexity | Notes |
|---------|-------------------|------------|-------|
| **Акт приёма-передачи (печатный)** — генерация из карточки устройства или сотрудника | Российская офисная реальность: при выдаче техники оформляют акт в 2 экз. (работодатель/сотрудник). Обязательные реквизиты подтверждены практикой (assistentus, glavbukh, e-kontur): организация, дата, ФИО/должности сторон, наименование + модель + серийник + инвентарник + стоимость, состояние, комплектность, подписи. Данные уже есть в приложении на 100% — осталась вёрстка. Аналог у Snipe-IT — подпись/EULA на выдаче; для RU-офиса печатный акт ценнее электронной подписи | **M** | Печатная HTML-страница + print-CSS (браузер сам делает PDF; PDF-библиотека не нужна). Два входа: одна позиция (карточка устройства, диалог «Выдать» с чекбоксом «распечатать акт») и пакетный акт «список выданного сотруднику» (карточка сотрудника — списки уже там). Реквизиты организации/руководителя — одноразовый диалог с сохранением в localStorage. Не строить редактор договоров: свободная форма, распечатал, ушёл. Ближайший к table-stakes в RU-практике кандидат |
| **QR-этикетки на устройства** (печать листа этикеток с QR, ведущим на карточку) | Snipe-IT: QR = deep-link на карточку, читается любым телефоном без установки чего-либо; Asset Panda строит вокруг этого весь продукт. Сценарии: маркировать новую партию (клон ×50 → печать 50 этикеток — идеально стыкуется с существующим bulk-выделением чекбоксами), найти устройство на полке, инвентаризация «вживую» | **S–M** | S: QR на карточке + печать листа от выделенных чекбоксами (qrcode-библиотека, фиксированная сетка на A4). M: если делать настраиваемые размеры/поля под конкретную этикеточную бумагу. **Критично:** НЕ делать встроенный сканер в браузере (см. Anti-Features) — камера телефона штатно открывает QR-URL. Внутренняя сеть = телефон в офисном Wi-Fi достаёт сервер. Плюс: дешёвый USB-сканер штрихкодов уже «работает» сегодня — он печатает инвентарник в существующий поиск по подстроке, ноль кода |
| **Сводка для руководства** (агрегаты: стоимость и количество по типам/отделам/годам закупки; гарантийный прогноз по месяцам; печатная одна страница) | В ITAM-софте самые ценные отчёты для руководства — cost summary и department attribution (OfficeSpace, Oracle, InvGate). Barahlo уже умеет отдать список (CSV/XLSX), но не «вывод на одну страницу для совещания»: сумма парка, стоимость по отделам, сколько устройств ждёт гарантийный в каждом квартале | **S–M** | S: блок агрегатов на дашборде (group-by запросы — паттерны уже есть в tile-запросах) + «печать текущего вида» (print-CSS списка с фильтрами). M: отдельная печатная «сводка» с несколькими таблицами. Гарантийный прогноз = расширение существующего блока гарантии дашборда (те же warrantyPredicate-композиции — parity by construction сохраняется). НЕ делать конструктор отчётов (см. Anti-Features) |

### Anti-Features (вымолено индустрией, но для одного пользователя — ловушки)

| Feature | Why Requested | Why Problematic | Alternative |
|---------|---------------|-----------------|-------------|
| **Email/push-напоминания об истекающей гарантии** | Стандарт ITAM («alerts must run natively», Invgate/Setyl) — но он рассчитан на команду, которая НЕ открывает систему ежедневно | SMTP-инфраструктура на внутреннем сервере, cron, настройка — недели обвязки ради аудитории из одного человека, который и так открывает приложение каждый день; alert fatigue подтверждён практикой | Уже построено: блок гарантии дашборда + жёлто-красная подсветка + фильтр окна гарантии. Saved view «Гарантия < 30 дн» (кандидат выше) закрывает напоминание за S |
| **Встроенный QR-сканер в браузере** | «Как у Asset Panda — навёл камеру» | getUserMedia требует secure context (HTTPS) — на внутреннем http-сервере API камеры просто заблокирован браузером; самописный сканер = L-сложность и хрупкость | Камера телефона штатно распознаёт QR и открывает URL — ноль кода. Печатать QR-этикетки (кандидат выше) |
| **Конструктор отчётов / произвольные выборки** | «Дадим пользователю свободу» | Конфигурируемость убивает одиночный инструмент: UI конструктора дороже всех отчётов вместе, а используется 2 раза. Известная ловушка однопользовательских инструментов | 2–3 фиксированные сводки (кандидат выше) + XLSX произвольного фильтра (уже в v1.3) |
| **Амортизация / бухгалтерская стоимость** | «Начальство спросит про износ» | Домен бухгалтерии, не оперативного учёта: методики, даты, интеграция с 1С. Даже у Snipe-IT depreciation report — хронически слабое место (GitHub #10749: нет retrospective-дат) | XLSX с закупочными ценами уже отдаёт бухгалтерии сырьё |
| **Комплекты (kits) как сущность** | «Выдаю набор ноут+док+монитор» | Новая сущность, UI, правила каскада — ради операции, которую bulk-выдача уже закрывает за 3 чекбокса | Существующая bulk-выдача; акт (кандидат выше) печатает весь набор одним документом |
| **Планируемая дата возврата (expected checkin)** | Snipe-IT умеет «выдать до 15.03» | Новое поле в movements → рябь по replay/валидации/правке истории (сильнейшая зона регрессии v1.2) ради слабого сигнала: руководитель видит сотрудников лично | Ничего; пересмотреть, если появится реальный запрос «возвраты теряются» |
| **Нативное мобильное приложение** | «Удобно с телефона» | Абсурдно для одного пользователя: сторы, сборка, релизы | Responsive-полировка (table stakes выше) |
| **Роли / самообслуживание / заявки** | Классический feature creep ITAM | Прямо противоречит стабильным решениям проекта (один аккаунт, без ролей) | Не принимать даже как «на будущее» |

## Feature Dependencies

```
[Сохранённые виды]
    └──requires──> (уже есть) URL-синхронизация фильтров/поиска + deep-link'и дашборда

[Акт приёма-передачи]
    └──requires──> (уже есть) movement-записи выдачи, поля устройства (модель/серийник/инвентарник/стоимость), ФИО+отдел
    └──requires──> реквизиты организации/руководителя (новое: одноразовый ввод, localStorage)

[QR-этикетки]
    └──requires──> (уже есть) bulk-выделение чекбоксами, URL-схема карточек, автогенерация инвентарника
    └──enhances──> [Клон ×N] (партия клонов → партия этикеток одним проходом)
    └──enhances──> [Мобильная эргономика] (QR ведёт в мобильный просмотр карточки)

[Сводка для руководства]
    └──requires──> (уже есть) tile-запросы дашборда, warrantyPredicate
    └──enhances──> [XLSX v1.3] (печатная страница vs файл — два носителя одного содержания)

[Быстрые действия из списка]
    └──requires──> (уже есть) bulk-диалоги выдачи/приёма (переиспользование server action)
    └──conflicts──> [чекбоксы bulk] в одной строке — раскладку строки решать до имплементации

[Мобильная эргономика] ──enhances──> [Лайтбокс фото v1.3], [QR-этикетки]
```

### Dependency Notes

- **Акт** — единственный кандидат с новой входной информацией (реквизиты сторон), и та хранится в localStorage, не в схеме. Ни один кандидат не требует миграции БД — это главный признак отсутствия scope creep.
- **Быстрые действия vs чекбоксы** — единственный дизайнерский конфликт: обе механики живут в строке списка. Решение на уровне UI-SPEC до фазы (например, кнопка появляется при hover/focus, чекбокс статичен).
- **Saved views (localStorage) vs БД** — выбрать одно хранилище и не смешивать. Для одного пользователя localStorage правилен; если когда-нибудь появится второй пользователь (вне скоупа), миграция localStorage→БД тривиальна.

## MVP Definition (рекомендуемая выборка для v1.3 — владелец выбирает из списка)

### Launch With (сильные кандидаты в v1.3)

- [ ] **Акт приёма-передачи** — самая высокая реальная ценность в RU-офисе; данные на 100% есть; M
- [ ] **Сохранённые виды** — S, ежедневная экономия, обобщает уже построенные deep-link'и
- [ ] **QR-этикетки (простая версия)** — S в базовой форме; стыкуется с клоном и bulk-выделением

### Add After Validation (если владелец хочет ещё)

- [ ] **Быстрые «Принять/Выдать» из списка** — S–M; после saved views, чтобы не перекраивать строку дважды
- [ ] **Сводка для руководства (печатная)** — S–M; после XLSX, чтобы не дублировать содержание
- [ ] **Мобильная полировка** — S; одной волной после лайтбокса

### Future Consideration (v2+, при реальном запросе)

- [ ] Планируемые даты возврата — только если «возвраты теряются» на практике
- [ ] Действия из ⌘K-палитры — палитра сейчас поиск, добавление действий = L-дрейф
- [ ] Настраиваемые макеты этикеток — только если простая сетка A4 не устроит

## Feature Prioritization Matrix

| Feature | User Value | Implementation Cost | Priority |
|---------|------------|---------------------|----------|
| Акт приёма-передачи (печатный, 1 позиция + пакетный) | HIGH | M | P1 |
| Сохранённые фильтры/виды (localStorage) | HIGH | S | P1 |
| QR-этикетки (QR на карточке + печать листа) | MEDIUM–HIGH | S–M | P1–P2 |
| Быстрые «Принять/Выдать» из списка | MEDIUM–HIGH | S–M | P2 |
| Сводка для руководства (агрегаты + печать вида) | MEDIUM | S–M | P2 |
| Мобильная эргономика (полировка) | MEDIUM | S | P2 |
| Печатная выгрузка текущего списка | MEDIUM | S | P2 (бесплатная часть «Сводки») |
| Email-напоминания о гарантии | LOW (для 1 пользователя) | M | Anti-feature |
| Встроенный QR-сканер | LOW | L | Anti-feature |
| Конструктор отчётов / амортизация / kits / expected-return | LOW | M–L | Anti-feature / defer |

**Priority key:** P1 — предлагать владельцу в первую очередь; P2 — предложить как второй эшелон; Anti-feature — активно отговаривать, давая альтернативу.

## Competitor Feature Analysis

| Feature | Snipe-IT (open source) | Asset Panda (SaaS) | Our Approach |
|---------|------------------------|--------------------|--------------|
| Saved searches/views | Фильтры списков + custom reports | Saved searches на custom fields | Saved views = имя + существующий URL-фильтр; localStorage; S |
| Labels/QR | Чекбоксы → Generate Labels; 1D barcode (asset tag) + 2D QR (deep-link); макет в Settings>Labels | Печать своих тегов + сканирование камерой | QR-этикетки от bulk-выделения; БЕЗ встроенного сканера (камера телефона открывает URL); USB-сканер уже работает через существующий поиск |
| Acceptance при выдаче | Digital signature + EULA на checkout | Подтверждение в мобильном приложении | Печатный акт приёма-передачи в 2 экз. — сильнее для RU-офиса, ноль юридической самодеятельности |
| Reports | Activity, Audit, Depreciation, Expiring, Custom export | Dashboards + custom reports | Фиксированная «Сводка для руководства» + XLSX (v1.3); без конструктора |
| Notifications | Email alerts: warranty/license expiry, expected checkin | Push в мобильном приложении | Anti-feature: дашборд-блок + saved view покрывают одного ежедневного пользователя |
| Mobile | Mobile-friendly + нативные приложения (beta) | Mobile-first, камера как главный инструмент | Responsive-полировка ключевых поверхностей; нативное — anti-feature |
